# Cycle Exchange Engine — личный вклад

Этот репозиторий содержит мою часть backend-разработки сервиса многостороннего обмена товарами.

Моя зона ответственности — жизненный цикл заявок на обмен, кластеризация похожих заявок, поиск циклических вариантов обмена, отклики пользователей, мягкая блокировка цепочек и подбор замены при отказе участника.

> Некоторые файлы являются интеграционными: в них есть код, написанный до моей доработки. Они включены только там, где содержат реализованную мной бизнес-логику. Основные самостоятельные реализации и тесты находятся в `src/backend/internal/service/matching`, `src/backend/internal/service/cluster`, `src/backend/internal/service/exchange_offer` и `src/backend/tests`.

## 1. CRUD заявок на обмен

Реализовал полноценную сущность `ExchangeOffer` и операции создания, просмотра, получения списка, изменения и удаления заявок.

Ключевые детали:

- слой `entity → repository → service → handler`;
- optimistic locking при изменении заявки;
- запрет изменения заявки, участвующей в заблокированной сделке;
- пересборка производных данных matching после изменения или удаления заявки;
- бизнес-ошибки, HTTP-контракты и тесты.

Заявка — первичный источник данных для алгоритма. Если после редактирования оставить старый кластер или старую цепочку, пользователю будет показан обмен с неактуальными товарами и желаниями. Поэтому изменение заявки не ограничивается SQL-обновлением: оно запускает локальное обновление matching-данных.

## 2. Кластеризация похожих заявок

Кластер объединяет взаимозаменяемые заявки: например, несколько пользователей отдают похожие товары и ожидают товар одного типа. Такой кластер может участвовать в нескольких вариантах цепочки, а конкретная заявка выбирается уже в процессе откликов.

Реализовано:

- поиск похожих заявок по двум embeddings через `pgvector`: для отдаваемого товара и желаемого товара;
- обновление кластера после создания или изменения заявки;
- проверка совпадения категорий, порогов similarity и направления обмена;
- обработка нескольких заявок в одном кластере;
- локальная пересборка затронутых данных вместо пересчёта всей базы.

Почему используются кластеры: похожие заявки можно хранить независимыми вершинами графа. Однако если в нескольких позициях маршрута есть альтернативы, это порождает множество вариантов, отличающихся только заменой одной похожей заявки. Кластер представляет одну обменную роль — группу взаимозаменяемых заявок с близкими характеристиками «отдаю» и «хочу получить». Поэтому поиск сначала находит маршрут на уровне ролей, а конкретная заявка выбирается позднее направленным голосом. Это уменьшает число дублей в выдаче, стабилизирует маршрут при появлении похожей заявки и даёт локальный пул для быстрой замены при отказе участника.

Как определяется кластер: заявка может войти в кластер только при совпадении категории отдаваемого товара и желаемой категории, а также достаточном similarity **обоих** направлений. Для заявок без категории дополнительно сравниваются прямое и перекрёстное направления, чтобы «отдаю» и «хочу» не были перепутаны. После изменения состава сохраняются технические характеристики кластера: центроид — средний embedding отдаваемых товаров — и `epsilon`, максимальная дистанция участника до центроида. В текущей версии они хранятся как описание компактности кластера; решение о включении пока принимается по попарным проверкам заявок, а не по дистанции до центроида.

Правило для поиска обменной стрелки: если пользователь указал `wanted_category`, кандидатный товар обязан иметь эту же категорию. Поэтому высокая близость описаний сама по себе не создаст обмен между разными категориями. Если желаемая категория не указана, остаётся векторная проверка; в пользовательском сценарии категория сейчас обязательна.

Почему используется локальное обновление: полный пересчёт всех заявок после каждого редактирования дóрог и создаёт лишние изменения. У заявки есть ограниченная окрестность похожих кандидатов, поэтому достаточно пересобрать затронутый кластер и цепочки, связанные с ним.

## 3. Поиск циклических цепочек

Реализовал `CycleFinder` на DFS для поиска простых циклов обмена длиной от 2 до 5 участников.

Направление `A → B` означает, что участник A передаёт свой товар участнику B. Цикл валиден, когда каждый участник получает желаемый товар от предыдущего участника:

```text
A → B → A

A → B → C → A
```

Алгоритм:

1. Для новой или обновлённой заявки загружаются Top-K подходящих исходящих рёбер.
2. Из них строится локальный ориентированный граф.
3. DFS ищет простые циклы с ограничением длины.
4. Для найденного цикла создаётся `ChainDraft`.
5. Кандидат проходит проверки направления, категорий, порогов similarity и уникальности пути.
6. Валидные варианты сохраняются как `CANDIDATE` и дедуплицируются по сигнатуре кластеров.

Почему поиск ведётся по кластерам: при нескольких похожих заявках на каждой позиции один и тот же смысловой маршрут превращается в набор почти одинаковых комбинаций конкретных заявок. Кластер позволяет найти маршрут один раз, а конкретного участника выбрать позднее голосованием. Поэтому на этапе подбора достаточно найти корректный цикл совместимых кластеров.

## 4. Кандидатные цепочки и отклики

Реализовал хранение и обработку найденных вариантов обмена.

Отклик является направленным: пользователь выбирает конкретную заявку, товар которой он хочет получить в этой цепочке. Для этого в голос добавлен `target_request_id`.

Реализовано:

- сохранение и дедупликация `CANDIDATE`-цепочек;
- получение доступных вариантов обмена для конкретной заявки;
- отправка и отмена отклика;
- проверка владельца заявки, позиции в цепочке и направления обмена;
- идемпотентность повторных запросов;
- поиск замкнутого цикла среди `pending`-голосов;
- переход цепочки в `PROPOSED` после полного набора откликов;
- фиксация выбранных конкретных заявок из кластеров.

Почему голос направленный: кластер может содержать несколько альтернатив. Голос «за кластер» не отвечает на вопрос, товар какой именно заявки пользователь хочет получить. Пара `request_id + target_request_id` делает выбор однозначным и позволяет проверить, что отклики действительно замкнули конкретную цепочку.

Почему переход в `PROPOSED` происходит только после замыкания голосов: отклик одного участника не означает согласия всей сделки. Замкнутый набор направленных `pending`-голосов подтверждает, что каждый участник выбрал конкретный товар, который хочет получить от следующего звена. После этого цепочку можно перевести в мягкую блокировку; окончательное подтверждение сделки происходит на следующем этапе.

## 5. Откат и быстрая замена

Реализовал обработку отказа участника на стадии предложения сделки.

Если отказавшаяся заявка входит в кластер с альтернативами, система ищет свободные активные заявки из того же кластера и возвращает их пользователю, ожидающему товар отказавшегося участника. Пользователь сам выбирает замену, а выбранный кандидат отдельно подтверждает участие.

Если замены нет, зависимые голоса очищаются, статусы восстанавливаются.

Почему замена не выбирается автоматически: similarity показывает техническую совместимость, но не заменяет согласие пользователя. Автоматическая подстановка могла бы вовлечь человека в сделку, которую он не видел и не подтверждал.

## Технические решения

- `pgvector` используется для семантического поиска, а категории и пороги similarity уменьшают ложные совпадения.
- DFS ограничен длиной цикла и Top-K кандидатами, поэтому поиск остаётся контролируемым.
- Дедупликация выполняется на уровне кластеров: один и тот же маршрут не размножается из-за близких заявок.
- Операции голосования идемпотентны, поэтому повторный клик или повторная доставка HTTP-запроса не создают дубликаты.
- Критические изменения цепочек выполняются транзакционно, чтобы конкурентные действия не оставляли частично обновлённые статусы.
- При изменении заявки пересобираются только зависимые кластеры и цепочки.
